
`49_acid_recovery`、`50_undo_clr` 两阶段崩溃注入通过。

### 3.3 崩溃注入关键数据

**49_acid_recovery**（崩溃发生在「未提交 UPDATE」之后）：

```text
[phase1 exit=1]        ← \crash 使进程非 0 退出，崩溃生效
Phase2 首查：id=1 bal=100  id=2 bal=50   ← 未提交的 UPDATE(999) 被 WAL undo 回滚
Phase2 末查：id=1 bal=100  id=2 bal=60   ← 已提交的 UPDATE(+10) 持久化；ROLLBACK 生效
```

**50_undo_clr**（崩溃发生在 ROLLBACK 撤销第 1 步之后）：

```text
[phase1 exit=1]        ← \crash_after_undo_steps 1 使进程在撤销中途崩溃
[crash-after-undo-steps] triggering _Exit(1) after undo step
Phase2 查询：仅 3 行（1|100, 2|200, 3|300）  ← 4/5/6 行的插入由 CLR 链补做完整 undo
```

两套用例验证了：WAL-before-data、redo 重放、undo 回滚、CLR 链在崩溃中断后继续完成撤销、已提交数据持久性。

## 4. 测试中发现的问题与解决方案

### 4.1 问题 A：PowerShell/.NET 管道注入 UTF-8 BOM，首条语句词法错误（阻塞性问题）

- **现象**：崩溃注入两阶段用例（49/50）在脚本化运行时偶发/持续报
  `Error: [Lexical] line=1, col=1: unexpected character: '�'`，随后连锁出现
  `table not found: acct` 语义错误；手工在终端输入或 `cmd` 文件重定向 `(`<``)` 均正常。
- **定位过程**：
  1. 用 `diag_run.ps1` 逐行打印**写入** stdin 的字节，确认写入内容为干净 ASCII
     `43 52 45 41 54 ...`（无 BOM），排除脚本编码问题；
  2. 对比 `Get-Content -Raw | & exe` 与 `.NET Process.StandardInput` 两种喂入方式，
     并试验 CRLF/LF、单块/逐行、StreamWriter/BaseStream 全部组合；
  3. 临时在 `src/main.cpp` 增加逐行 hex dump 插桩，复现后证实**进程实际读到的首行**
     前缀为 `EF BB BF`（UTF-8 BOM）——即 Windows PowerShell/.NET 向子进程管道写入
     首批输入时自动附加了 BOM 前导（`.NET Framework StreamWriter` 使用带 BOM 的
     `UTF8Encoding`），而写入方日志显示的是清洗后的字节。
- **根因**：编译器 REPL 未处理输入流首部 BOM；BOM 首个字节 `0xEF` 被词法器判为
  「非法字符」，首条语句失败 → 建表未执行 → 后续语句全部连锁失败 → Phase2 无表可恢复。
- **解决方案**（代码级修复，见 §4.1 修复清单）：
  1. `src/main.cpp`：`std::getline` 读入每行后，若行首为 `EF BB BF` 则剔除（BOM 只可能
     出现在输入开头，清除后不影响任何合法 SQL）；该修复同时惠及「用户重定向 Notepad
     保存的带 BOM 脚本」等真实场景，属于 CLI 健壮性增强；
  2. `tests/run_sql_regression.ps1`：执行器路径由陈旧的 `build\Debug\sqlcompiler.exe`
     更正为当前构建产物 `build\sqlcompiler.exe`（MinGW 单配置构建输出在 `build\` 根）；
  3. 同步更正 `tests/run_all_tests.bat`、`tests/run_acid_recovery.bat`、
     `tests/run_acid_clr.bat` 的 `BUILD_DIR` 为 `%ROOT_DIR%\build`。
- **验证**：修复后 49/50 两阶段用例连续多轮通过（PASSED=55 FAILED=0），
  `storage_ut` 58325 checks / 0 fails 不受影响。

### 4.2 问题 B：单元测试输出残留调试打印，污染测试证据

- **现象**：`storage_ut.exe` 输出中出现 `[DBG-rb] txn=... undo page=...`、
  `[DBG-del] ...` 等临时调试行。
- **解决方案**：删除 `src/txn/TransactionManager.cpp` Rollback 循环内的无条件
  `std::cerr << "[DBG-rb]..."` 与 `tests/storage/storage_ut.cpp`
  TestSnapshotDeleteFcw 内的 `[DBG-del]`/`[DBG-del-idx]` 打印（断言 CHECK 保留）。
- **验证**：重建后输出干净，仅保留有意设计的基准输出（`[low-water]`、`[Phase4] group-commit`、`==== OS 模块性能对比基准 ====`）。

### 4.3 问题 C：构建产物路径不一致

- **现象**：`build\Debug\` 下存在旧版 `sqlcompiler.exe`（与当前源码不一致），
  多个测试脚本引用该陈旧路径。
- **根因**：工程 CMake 生成器为单配置 **MinGW Makefiles**（`CMAKE_BUILD_TYPE=Debug`），
  产物直接输出到 `build\` 根目录；`build\Debug\` 是历史遗留的陈旧产物。
- **解决方案**：统一测试脚本指向 `build\sqlcompiler.exe`（见 §4.1）。
