# 操作系统模块优化方案建议书（2026-09）

- 项目：小型数据库系统 SQL-Compiler（编译原理 + 操作系统 + 数据库 三模块综合实训）
- 输入依据：[OS_Module_CodeReview_Report.md](./OS_Module_CodeReview_Report.md)（代码审阅发现的 6 项已知限制）
- 文档用途：支撑项目汇报「优化路线论证」环节

---

## 一、优化目标与原则

基于审阅报告的已知限制，本轮优化目标按优先级排序：

| 优先级 | 目标 | 对应限制 |
|---|---|---|
| P0 | B+Tree 写并发从树级升级到页级（不破坏正确性） | 树级粗粒度锁 |
| P0 | 版本回收不依赖后台线程（快照水位 O(1) 化） | 真空依赖后台线程 |
| P1 | 锁管理热路径可扩展（升级自适应、锁表分片） | 阈值固定、全局互斥 |
| P1 | 索引陈旧条目可回收（延迟摘除 → 可回收墓碑） | 二级索引 MVCC 仅过滤不回收 |
| P2 | 谓词锁检索从线性扫描到对数 | 谓词仅主键键空间、扫描 O(P) |
| P2 | 持久化吞吐（组提交 + 温度感知刷盘） | 每次同步落盘、刷盘无调度 |

**原则**：① 每阶段延续「实现 → 测试（UT+SQL 回归+崩溃注入）→ 文档 + 前后对比数据」闭环；② 保持与课程知识点的可映射性（分页、置换、锁、死锁、磁盘 I/O、崩溃恢复）；③ 不引入外部依赖、不重写存储层。

## 二、开发路线图（分阶段、含独特创新特性）

### Phase 0：基线固化（1 轮）
- 动作：以 6982 checks / 55 SQL 回归为基线，补充并发基准脚本（多会话 DML 吞吐、锁表条目数、真空滞后页数、谓词检查耗时）。
- 产出：性能基线报告（后续每阶段前后对比的「前」数据）。

### Phase 1（创新特性 A）：B+Tree 乐观页级并发
- **问题**：树级锁使不同键空间的写者串行（`Insert`/`Delete` 全树互斥），多连接写并发为 0。
- **方案**：树节点访问改为**页级读写闩 + 乐观重启（optimistic restart）**：
  - 读路径：`BeginRead` 记 `version` → 遍历 → `EndRead` 校验版本未变，否则重启（读不阻塞写、无锁等待）；
  - 写路径：`OptimisticLatchCoupling`——下行时取闩→校验上节点版本→必要时升级写闩，冲突即局部重启而非等待；
  - 结构变更（分裂/合并）用 **写闩 + 版本号 CAS** 发布，读端可见性由版本校验保证；
  - 复用现有 `PageReadGuard/PageWriteGuard` RAII 与锁序约束，不改页头格式（版本号置于页头既有保留字段）。
- **创新点**：把操作系统「读者-写者锁 + 版本号校验」思想用于 B+Tree 遍历，**避免锁等待死锁**（无等待图、无 DFS），与现有死锁检测正交。
- **验收指标**：多会话异键空间并发 INSERT 吞吐 ≥ 现状 3×；storage_ut 并发用例不出现死锁/超时；SQL 回归全绿。

### Phase 2（创新特性 B）：O(1) 快照水位 + 无后台真空
- **问题**：`OldestActiveSnapshot` 遍历活动快照表 O(N)；`Vacuum` 依赖后台线程（默认关闭）。
- **方案**：
  - **全局低水位缓存**：CommitTracker 维护单调低水位 `low_water_mark`（= 所有活跃快照 CSN 的最小值），用「活跃快照计数 + 全局 CSN 序列」增量维护——快照 Begin 时若其 CSN < low_water 则降水位，Commit/Rollback 时用惰性推进（延迟重算）；`OldestActiveSnapshot` 变为 **O(1) 读缓存**；
  - **内联轻量真空**：写路径（Update/Delete 写新版本时）顺带回收「本页内已确认 < 低水位」的旧 slot（上限每语句 k 个，摊薄成本），后台真空保留为「低频兜底」而非唯一通道。
- **创新点**：快照水位从「每次 O(N) 扫描」变为「事件驱动 O(1) 缓存」，版本回收从「依赖后台线程」变为「写路径内联摊薄 + 后台兜底」双通道。
- **验收指标**：1 万活跃快照下 `OldestActiveSnapshot` 耗时恒定（O(1)）；真空滞后（未回收版本数）下降 ≥ 60%；长事务下无版本误删（复用现有真空边界测试）。

### Phase 3（创新特性 C+D）：自适应锁升级 + 索引墓碑回收
- **问题**：升级阈值固定 128；快照写者延迟摘除的索引旧条目永不回收。
- **方案**：
  - **自适应升级阈值**：`kThreshold(table) = f(表估计行数, 本事务已持行锁数, 采样冲突率)`——小表提前升级（省登记开销），大表延后（避免不必要表锁阻塞他人）；升级冲突率由 `TryEscalateTable` 的 `kWouldBlock` 采样累计；
  - **索引墓碑回收**：把 t4 的「延迟保留旧条目」升级为「带墓碑的惰性条目」——快照读者经过键重检后可在**无活动快照引用**时（条目版本 end_csn < 低水位）标记墓碑；后台索引真空批量摘除墓碑条目（按低水位判定安全），不破坏唯一索引急切语义。
- **创新点**：锁升级从「静态阈值」变为「数据驱动自适应」；索引 MVCC 从「只过滤不回收」变为「可回收墓碑 + 水位安全判定」。
- **验收指标**：批量写 128 行表提前升级、10 万行表延迟升级（按表自适应）；二级索引墓碑条目在低水位推进后被回收（索引大小收敛测试）。

### Phase 4（创新特性 E+F）：谓词锁区间树 + 持久化吞吐
- **问题**：谓词检查线性扫描 O(P)；每次提交同步刷 WAL/数据（吞吐受 fsync 频率限制）。
- **方案**：
  - **谓词区间树**：谓词表按（表, 区间）组织为**平衡区间树/有序集合**，`CheckWritePredicate` 变为区间重叠查询 O(log P)；全表谓词作为全域区间哨兵；
  - **WAL 组提交**：提交按 CSN 批次聚合一次 fsync（组内提交延迟 = 批次窗口），数据页刷盘改为**温度感知**（脏页按访问频率分级，冷页优先刷、热页留池）——沿用 `writeback_count` 统计扩展出「刷盘温度分布」。
- **创新点**：把「有序索引」思想引入锁表结构；把「组提交 + 冷热分离刷盘」这一操作系统/文件系统经典手段落地到 WAL 与缓冲池。
- **验收指标**：1 万谓词条目下写前检查耗时从 O(P) 到 O(log P)；组提交下事务提交吞吐 ≥ 现状 2×；崩溃注入 49/50 仍 exit 0。

## 三、所选方案论证（Justification）

1. **与现有架构兼容（零破坏）**：所有阶段复用既有接口——页锁 RAII、`PageReadGuard`、`SetSnapshot/CommitTracker`、`IndexMaintenance` 延迟摘除、`OsModuleOptimizations` staged 模式；不改页头/文件格式（版本号用保留字段），`.fpl/.crc/WAL` 格式零变更 → 旧库向后兼容、崩溃恢复语义不变。
2. **风险可控、可回退**：每阶段独立成「开关/环境变量可配」的优化（延续 `SQLCOMPILER_BG_FLUSH_MS` 模式），基准失败即回退；Phase 1 的乐观重启与现有 DFS 死锁检测正交，最坏情况退回树级锁。
3. **收益聚焦已知瓶颈**：审阅报告确认 6 项限制中，树级锁与真空回收是「并发与空间」两大核心痛点（P0），其余为扩展性/吞吐（P1/P2）——路线图按痛点优先排列，每阶段都有可量化验收指标。
4. **教学可映射性**：Phase 1（读者-写者锁/乐观并发）、Phase 2（快照/GC 思想）、Phase 3（自适应调参）、Phase 4（索引结构/组提交/冷热分离）分别对应操作系统「锁与死锁」「内存回收」「自适应策略」「I/O 调度」章节——汇报时可逐阶段映射知识点。
5. **工程量可控**：全程增量修改（预估单文件级改动为主），不新增大型子系统；测试复用现有 6982 checks 基建 + 每阶段新增并发/边界用例。

## 四、拒绝的替代方案与理由（Rejected Alternatives）

| 替代方案 | 为何被考虑 | 拒绝理由 |
|---|---|---|
| **完全乐观并发（OCC 全覆盖，去锁基）** | 写写不阻塞、无死锁，是 MVCC 数据库主流 | ① 与课程「锁/死锁检测」章节冲突——本模块需展示多粒度锁与 DFS 检测；② 写偏斜/冲突检测重试成本在写密集负载下劣化；③ 需重写事务/执行器接线，工程量超出本模块范围且风险高 |
| **全表锁退化（回到 T1）** | 实现最简单、零并发 bug | 并发归零，直接违背「多连接并发事务」项目目标，且使既有行锁/谓词锁成果全部失效 |
| **朴素页级锁（无乐观重启的 crabbing）** | 页级并发直观 | 层间锁序 + 父节点升级互斥会产生锁等待环（需持父闩等子闩），与现有「无等待图」设计冲突；不解决读-写互斥下的吞吐损失——乐观重启是更优形态 |
| **同步/立即真空（前台语句内全量回收）** | 空间归还最及时 | 每语句同步回收放大写延迟（写路径被回收 I/O 拖累）；长事务下根本无版本可回收（低水位不推进）——同步无收益 |
| **高频率全库定时真空** | 实现简单 | I/O 放大，与业务争抢磁盘带宽；无水位感知时（旧实现）存在误删活动快照版本的数据安全风险（本项目曾出现） |
| **引入第三方嵌入式 KV（RocksDB/LevelDB）** | 现成 MVCC/LSM 能力 | ① 重写存储层，自研缓冲池/置换/锁/日志全部作废，丢失课程价值；② 外部依赖与实训环境（离线/无包管理）冲突 |
| **无限扩大缓冲池** | 提升命中率 | 逃避页面置换问题本身；掩盖 LRU-K 行为，失去「置换算法」教学内容；内存上限本就是本项目约束（默认 256KB） |
| **单写者全局串行化（Big Writer Lock）** | 写一致性最简单 | 写并发为 0，与 Phase 1 目标直接矛盾；仅可作极端回退选项，不作为主方案 |
| **MVCC 全多版本化（每写建新版本、无 in-place head）** | 彻底免锁读 | 空间放大（每行每写一份）、版本链变长拖累点查、二级索引复杂度剧增；与现有「head 原地覆写 + 单旧版本」紧凑布局冲突 |

## 五、验收与汇报口径

1. **每阶段产出**：实现 + 新增 UT（并发/边界/崩溃注入）+ 前后对比数据（吞吐、锁条目、真空滞后、检查耗时）+ 技术文档（沿用 .trae/documents 机制文档格式）。
2. **终态指标**（合计）：多会话写并发 ≥ 3×；`OldestActiveSnapshot` O(1)；索引墓碑可回收；谓词检查 O(log P)；提交吞吐 ≥ 2×；**storage_ut ≥ 7400 checks / 0 fails；SQL 回归 55 passed / 0 failed**（含崩溃注入）。
3. **汇报材料**：本建议书 + 各阶段机制文档 + 代码审阅报告构成「问题 → 方案 → 证据」三段式汇报主线。
