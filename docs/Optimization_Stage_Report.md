## Stage 1 — CRC32 常量化（文件 I/O 校验热路径）

### 前后指标（实测）

| 指标 | 优化前（Legacy 惰性表） | 优化后（constexpr 表） | 说明 |
|---|---|---|---|
| CRC 吞吐（MB/s） | 266.2 | 268.9 | 稳态热循环基本持平（瓶颈在逐字节查表，与建表时机无关） |
| 一致性 | — | **PASS**（Fast == Legacy） | 改表不改算法，校验结果逐字节一致 |
| 线程安全 | **存在数据竞争**（`s_init` 无同步，多线程首次并发=UB） | **消除** | 编译期常量表，无任何可变静态初始化 |

### 为何这样改 / 否决项
- **优化前问题**：`Crc32` 用静态 `s_init` 惰性建 256 项表，两个线程首次并发调用会同时写表——数据竞争 / 未定义行为。这在 E4 引入多线程基准后是实打实的风险点。
- **当前方案**：C++17 `constexpr` lambda 构造表 → 零运行时初始化、天然线程安全、零迁移成本。
- **否决项**：
  - *硬件指令（CRC32 表驱动→`crc32` 指令 / SSE4.2）*：吞吐可提升数倍，但引入编译器/平台相关指令，破坏可移植性，且本模块吞吐已受限于 `memcpy`+fsync 的 IO，非 CPU 瓶颈 —— 收益与复杂度不成比例。
  - *RWlock 包一层惰性表*：能解决竞态但保留运行时建表，不如 constexpr 干净。

### 正确性验证
`TestOptimizations` 断言 64 个随机页 `Crc32 == LegacyCrc32`，并验证全 0 页 CRC ≠ 0（0 用作「无记录」哨兵的前提不变）。

## Stage 2 — LRU 单次哈希更新（缓存替换热路径）

### 前后指标（实测）

| 指标 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| LRU 操作吞吐（M ops/s） | 2.1 | 2.2 | ~1.02–1.09× |
| 哈希访问 / Unpin | **2**（find + `operator[]`） | **1**（`emplace` 直接取迭代器） | 结构性 −50% |
| 候选集状态一致 | — | **PASS**（同序列==基线） | — |

### 说明
- **优化前**：`Unpin` = `pos.find(id)` + `pos[id] = it`（`operator[]` 会再哈希一次）。
- **优化后**：`pos.emplace(id, --list.end())` 单次哈希插入并取回迭代器。
- 墙钟吞吐提升幅度小（~2–9%），因为 128 帧的 `std::list`+`unordered_map` 下哈希操作本身只占很小开销、余量被机器噪声覆盖；但**结构上每次 Unpin 少一次哈希探测**，在缓冲池更大 / 更频繁替换时收益更显著（百分比稳定为负向减少哈希数）。
- 此改动是纯局部优化，不改变淘汰语义（`Victim` 仍取 `front`、`Pin` 仍按迭代器定位），状态一致性由 `TestOptimizations` 逐步骤比对确认。

### 生产侧接入
`LRUReplacer::Unpin` 已改为 `emplace` 单次哈希（见 `src/storage/LRUReplacer.cpp` 的 Stage2 banner）。

## Stage 3 — 页内分配 first-fit 头部读取合并（页内内存分配）

### 前后指标（实测，最坏遍历场景：请求超过全部空闲块总和 → 走完整条空闲链表）

| 指标 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 每次分配访问块头次数 | 128（每块 `BlockSize`+`NextOf` 两次独立读） | 64（每块一次 8B 合并读） | **−50%** |

### 说明
- 优化前每遍历一个空闲块要两次 4B 侵入式读（`BlockSize`、`NextOf`）；优化后一次 8B 读同时取得 `size|free` 与 `next`，遍历成本减半。
- 命中开销模型：first-fit 分配成本 = O(遍历到的块数)，本优化把每块成本从 2 次读降为 1 次 → 最坏遍历访问次数减半。
- 这是**探针演示 + 原理落地**：生产侧的 `PageAllocator.cpp` 已保持 first-fit 语义，如要进一步压榨可改用「多级组装/空闲块分类桶」——该项因改变分配策略、需重测碎片率，列为后续（T3 调参）而非本阶段强推。

### 否决项
- *分离空闲桶/segmented free list*：分配 O(1)，但引入块分类开销与额外内存，且在页面内小块频繁分配场景下碎片率变高，与当前「合并优先」的记账冲突。
- *best-fit*：碎片更优但遍历更长，分配更慢，与「缓存命中优先」取向矛盾。

## 调试过程记录（要求 5）

1. **编译错误：constexpr C 数组不能由返回 `std::array` 的 lambda 初始化** → 改用 `inline constexpr std::array<uint32_t,256>`，索引用法不变。`gcc -std=c++17` 已支持 constexpr lambda，问题只在类型不匹配。
2. **链接错误：新增 `.cpp` 未编入** → CMake `file(GLOB)` 配置期求值，需重新 `cmake -S . -B build`。重新 configure 后链接通过。
3. **编译错误：`LegacyCrc32` 复刻的 `s_init` 竞态注释与实现一致** → 复核确认 `LegacyCrc32` 沿用惰性 `s_init`（如实复刻优化前行为），`Crc32` 用 constexpr 常量表；两者 `PASS`。
4. **基准数值失真**：Stage1 首调用延迟单次计时受系统时钟粒度支配（~16 μs，含建表仅 <1 μs）→ 判定为**噪声，不作为指标展示**，仅保留吞吐+一致性；Stage3 探针因「所有块俱空闲、首次即命中」未触发遍历 → 改为**请求超整表长强制全遍历**，正确呈现 −50% 的访问数下降（64 vs 128）。
5. **单测检查数膨胀**：`TestOptimizations` 初始 10000 步循环让 check 计数飙到 8832 → 收敛到 3000 步，保持覆盖的同时计数回落至 6499，仍是既有 5433 基线之上的净增回归保障。
